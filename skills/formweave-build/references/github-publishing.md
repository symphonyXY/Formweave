# GitHub 发布：本地准备与远端授权分开

发布请求不改变实现范围或许可。先读取仓库指引和用户已有约定；没有改用其他规则的明确要求时不重配远端、改默认分支或修改保护策略。可在聊天中确认，也可从项目内用户批准的政策文件读取下列偏好；**持久偏好不是本次远端操作授权**。

| 可配置项 | 需要知道什么 |
|---|---|
| 目的地与可见性 | GitHub 主机、仓库所有者／名称、已存在还是要创建、仓库可见性；禁止把私有工程默认变成公开。 |
| 分支与提交 | 源分支及提交对象、目标分支、直推或 PR、提交格式、允许包含哪些暂存内容。默认不推 `main`，不强推，不修改已有提交。 |
| 版本与产物 | 沿用项目定版规则；标签及对应提交、草稿／预发行／正式 Release、附件与哈希、发布说明。不是每次推送都创建标签或 Release。 |
| 通过条件 | 适用的测试、干净副本启动、文档、许可、凭据扫描、CI 与审批；缺少的证据写未验证而非通过。 |

## 本地检查（不写远端）

1. 确认工作树、暂存区和拟发布的提交范围；分别列出用户改动、当前任务改动、未跟踪资材和不提交的生成物。核对远端地址时隐藏认证信息。未获准提交不创建提交；不能以批量暂存、提交或推送替用户选择范围。
2. 审查准备公开的提交和附件中是否含密钥、私有依赖、真实用户数据、机器路径、调试日志与未经授权的素材。忽略规则不作用于已经跟踪的内容或历史。可用 [Gitleaks v8.30.1 独立 CLI](https://github.com/gitleaks/gitleaks/blob/v8.30.1/README.md) 的 `git` 模式检查拟推范围，首次公开还要检查将公开的历史；`--redact` 保护日志，不把原始凭据或未审查扫描报告附入交付。命中时暂停发布并处理，不用扫描通过代替人工保密和许可审查。
3. 汇报仓库、分支、提交、标签、拟执行动作、变更摘要、测试、已核对附件与 SHA-256、授权缺口。报告可在本地生成；在线只读状态未检查或 CI 未运行时不要宣称远端已就绪。公开仓库的社区健康文件是[平台建议](https://docs.github.com/zh/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories)，不是统一的推送规范。

## 明确授权后逐项执行

- 只执行指令涵盖且目标清楚的远端动作。创建仓库、调整可见性、推分支或标签、开 PR、建 Release（包括草稿）、上传附件分别核对；一次明确指令可同时授权列出的多项。再次确认实际远端和提交对象与报告一致。遇到冲突、保护规则、验证失败、权限不足或身份不匹配就停止，不临时改目标、不绕过保护。
- 可使用 Git 或 [GitHub CLI v2.105.0](https://github.com/cli/cli/releases/tag/v2.105.0)。例如仅在授权创建 Release 后使用 [`gh release create` 的 `--verify-tag`](https://cli.github.com/manual/gh_release_create)，避免标签不存在时从默认分支隐式创建；仍须事先核对远端标签指向的提交。报告实际成功的远端对象和链接、未执行或失败的步骤，不把本地候选目录当作已经发布。
- [Release Please v17.11.2](https://github.com/googleapis/release-please/releases/tag/v17.11.2) 仅供已决定采用发布 PR 和提交约定的仓库评估；它能写入远端，不是本流程的默认运行器。优先保留用户现有版本字段和本地定版方式。
