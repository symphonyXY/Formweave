# 程序设计与交接

先按[范围确认](agreement.md)把信息分为已知、建议默认、需要决定、待实测。只问会改变数据、关键行为、成本或验收的问题。给用户具体场景、可选做法和推荐理由；可以并行调查的，不等回答才开始。不可逆动作的未知规则不能当默认批准。

## 选择深度

- 局部改动：写主行为、明确不变的旧行为、会失败的情形与复验步骤。例如「在筛选框增加快捷键；焦点移到输入框，旧快捷键仍有效；中文输入法处于候选状态时不误提交」。
- 多流程或高风险改造：选下面会影响实现的部分，给关键需求稳定编号，以便预览、开发和审查引用。用简表即可，不要求每个项目单独建多份文档。

| 内容 | 决定或交接什么 |
|---|---|
| 业务路径 | 谁从哪进入、输入是什么、哪些规则拒绝输入、成功产生什么；说明主路径和实际会出现的例外。 |
| 状态与后台任务 | 状态、触发条件、所有者、可执行动作和终态；明确取消、重试、重复点击、失败后的半成品、关闭后再打开如何处理。 |
| 数据与接口 | 来源、结构、验证、所有权、写入时机、存储与权限；已有版本的数据迁移要说明备份、失败后原数据与回滚。 |
| UI 与系统边界 | 每个主操作的界面入口、键盘、焦点、窄窗；区分原型假数据与真实服务，并标注只能在目标 Windows 验证的行为。 |
| 验收与交付 | 每条关键需求给前置条件、输入、动作、应观察到的结果和证据方式；保留系统、数据量、性能阈值、交付物及不在本轮范围的内容。 |

例如：`R-03 批量校验` 从启动时的所选编号生成处理快照。运行中改变筛选不修改快照；取消后只保留已完成项的回执。验证时先选三项、启动后改筛选，再于第一项完成后取消，断言三项范围不变、回执为完成一项且剩余任务停止。真实耗时或提交回滚策略未知时分别标注「待测」或「待决定」，不要借例子替用户决定。

交接可贴在聊天：已确认范围、关键需求与验收、待确认项、已知限制。实现后按同一编号记录通过、失败、未验证或不适用；不把「出方案」当作实施批准。需求追踪借鉴 [GitHub Spec Kit v1.4.2](https://github.com/github/spec-kit/blob/v1.4.2/spec-driven.md)，无需安装。
